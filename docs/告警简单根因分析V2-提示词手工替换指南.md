# 告警简单根因分析 V2 提示词手工替换指南

## 1. 文档用途

本文档用于在不重新导入工作流的情况下，直接在 Dify 工作流编辑页面中手工更新“告警简单根因分析 V2”的提示词。

本次仅调整 7 个 LLM 节点中的 User 提示词，主要解决以下问题：

1. EPOLL 升高时默认建议 `strace epoll_wait`、`perf trace epoll:*`，与实际网络排查方向不匹配。
2. 提示词将运行对象固定描述为 Pod 或容器，不适用于纯虚拟机环境。
3. `服务xx`、`xxx实例`、`XXXX告警`等示例占位词可能进入最终报告。
4. 下游影响和报告展示没有根据真实服务、实例及运行环境生成内容。

本次修改不会调整工作流节点、连线、并行层级、RTT 算法、Span 查询或 Trace 查询逻辑。

## 2. 使用前提

当前工作流应为“告警简单根因分析 V2”，并且已经包含以下环境上下文节点变量：

```text
{{#v2_runtime_environment_context.location_text#}}
{{#v2_runtime_environment_context.instance_term#}}
{{#v2_runtime_environment_context.prompt_context#}}
```

服务名使用以下已有变量：

```text
{{#1754299310647.service#}}
```

如果编辑器中无法选择或识别 `v2_runtime_environment_context` 变量，说明当前工作流版本较旧，不适合仅手工替换提示词，应先更新到包含环境上下文节点的 V2 版本。

## 3. 推荐操作顺序

1. 在 Dify 中复制或备份当前工作流。
2. 按本文档中的节点 ID 或节点名称定位节点。
3. 仅编辑节点的 User 提示词，不修改 System 提示词、变量、连线或节点配置。
4. 使用编辑器搜索原文本并替换，避免直接覆盖整段提示词。
5. 完成单个节点修改后先保存，再修改下一个节点。
6. 最后将“公共输出身份与环境规则”追加到全部 7 个节点的 User 提示词末尾。
7. 保存并发布工作流，使用虚拟机和容器场景分别验证一次。

## 4. 节点修改清单

### 4.1 可行动方向建议

- 节点名称：`可行动方向建议`
- 节点 ID：`1741512806512`

替换 1，运行对象描述：

原文本：

```text
基于服务层级聚合Pod信息并输出服务级概览报告。需确保各Pod具体运行状态的可视化呈现清晰直观。
```

替换为：

```text
基于服务层级聚合运行对象信息并输出服务级概览报告，清晰呈现各主机进程、实例或 Pod 的实际运行状态。
```

替换 2，EPOLL 排查建议：

原文本：

```text
根因为EPOLL：strace -e epoll_wait,epoll_pwait -tt -T -p <PID>追踪epoll调用耗时，perf trace -e epoll:*查看epoll相关事件等命令
```

替换为：

```text
根因为 EPOLL：保留 EPOLL 作为异常方向，但建议从网络连接和等待原因排查。优先结合 RTT、下游 Span、超时和重传证据；可按证据选择 ss -s、ss -antp、nstat -az、sar -n TCP,ETCP 1、ip -s link。不要默认建议跟踪 epoll 系统调用，也不要机械输出全部命令。
```

替换 3，明细对象描述：

原文本：

```text
服务级汇总指标与Pod明细指标
```

替换为：

```text
服务级汇总指标与运行对象明细指标
```

## 6. 替换后的检查清单

完成修改后，在上述 7 个节点中搜索并检查：

- [ ] 不再包含 `strace -e epoll_wait`。
- [ ] 不再包含 `epoll_pwait`。
- [ ] 不再包含 `perf trace -e epoll:`。
- [ ] 不再包含 `服务xx`、`xxx实例`或`XXXX告警`等可进入报告的占位内容。
- [ ] EPOLL 仍然作为一个独立异常方向存在。
- [ ] EPOLL 建议中包含 RTT、下游 Span、超时或重传等网络证据。
- [ ] 虚拟机场景使用主机、进程或实例描述，不被固定写成 Pod。
- [ ] 容器场景仍可使用 Pod、OOMKill、K8s Event 等容器证据。
- [ ] 没有修改节点连线、条件分支和并行结构。

## 7. 建议验证场景

### 7.1 纯虚拟机场景

预期结果：

- 报告使用主机、进程、实例等词汇。
- 不建议检查 Pod、K8s Event 或 OOMKill，除非输入证据明确说明存在容器环境。
- 不因为工具结果出现“按Pod统计”而推断运行环境为容器。

### 7.2 容器场景

预期结果：

- 可以正常使用 Pod、节点资源、容器状态、OOMKill 和 K8s Event 等证据。
- 服务名和 Pod/实例名应来自实际输入变量，不出现占位符。

### 7.3 EPOLL 升高场景

预期结果：

- EPOLL 仍可以被识别为异常方向。
- 建议优先结合 RTT、下游 Span、连接状态、超时和重传进行排查。
- 可以根据已有证据选择 `ss -s`、`ss -antp`、`nstat -az`、`sar -n TCP,ETCP 1` 或 `ip -s link`。
- 不再默认建议跟踪 `epoll_wait`、`epoll_pwait` 或所有 EPOLL 系统调用。

### 7.4 信息不完整场景

预期结果：

- 服务名为空时省略服务字段。
- 下游服务不明确时保留“下游依赖问题”的通用描述，不编造具体服务。
- 业务功能、延时和错误率数据缺失时不生成虚假数值。

## 8. 回退方式

如果修改后输出异常，可从工作流备份中恢复这 7 个节点的 User 提示词。回退时不需要调整节点连线、代码节点或并行结构。
